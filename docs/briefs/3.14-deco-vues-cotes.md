# 3.14, point 5 : vues du gabarit, emplacements par vue, gauche et droite (proposition)

Date : 19/10/2026. Statut : **proposition, point d'arrêt**. Aucun code modifié, aucune migration, aucune écriture en base.

Sources lues : `src/apps/voiture/gabarits/saxo.ts`, `types.ts`, `index.ts`, `gabarits.test.ts` ; `src/apps/voiture/plan.ts` ; `regles.ts` (`emplacementsDepuisGabarit`) ; `services-serveur.ts` (création du véhicule, `modifierEmplacementDans`) ; `lectures-serveur.ts` ; `lectures-partagees.ts` (`listerEmplacementsPourPartenaires`) ; `libelles.ts` (`TITRE_VUE`) ; `prisma/schema.prisma` (`VoitureSlot`, `VoitureVue`) ; `docs/schema-voiture.md`.

## 1. Réponse à « comment la symétrie est stockée aujourd'hui »

Elle est stockée **deux fois**, dans deux lignes de `voiture_slot`. Ce n'est pas seulement un affichage.

- Le gabarit Saxo déclare cinq types `symetrique: true` (Portière, Custode arrière, Aile avant, Aile arrière, Bas de caisse), en vue `droite`, avec `vuesDessinees: [droite, gauche miroirDe droite]`.
- `emplacementsDepuisGabarit` (`regles.ts`, ligne 90) crée, pour chaque type symétrique, **une ligne `droite` et une ligne `gauche`**, avec le même `nom`, le même `ordre`, `symetrique = true`, et **la même forme, non retournée**.
- Une Saxo compte donc 15 lignes : 10 pour les cinq symétriques, 1 pour le bandeau de pare-brise, 4 hors plan.
- Le plan (`plan.ts`, `emplacementsDessines`) ne dessine que les lignes `vue = droite`. La vue gauche redessine ces mêmes lignes en miroir (`miroirDeForme`). **Les lignes `gauche` ne sont jamais dessinées ni listées sur le plan.**
- La liste des emplacements pour Partenaires (`listerEmplacementsPourPartenaires`) prend **toutes** les lignes, sans filtre sur la vue, et ne renvoie pas la vue. Le choix d'emplacement d'une convention affiche donc « Portière » deux fois, sans côté. C'est la remarque de John.
- Le comptage des emplacements libres (`lectures-serveur.ts`, ligne 42) inclut aussi les lignes `gauche`.

Conséquence, à confirmer en base : une ligne `gauche` peut être réservée depuis une convention, et la réservation n'apparaît alors pas sur le plan. Je l'ai déduit du code, je ne l'ai pas observé (Docker arrêté).

Incohérence à noter : `modifierEmplacementDans` refuse `symetrique` hors de la vue droite (« Seul un emplacement du côté droit peut être symétrique à gauche »), alors que la création pose `symetrique = true` sur les deux lignes.

## 2. Ce qui est déjà prêt, sans migration

- `VoitureVue` contient déjà `droite`, `gauche`, `avant`, `arriere`, `dessus`, `hors_plan`. Aucune migration pour les vues.
- `VueGabarit`, `VUES` (services) et `TITRE_VUE` (libellés) couvrent déjà les trois vues manquantes.
- Le type `Gabarit` accepte de nouvelles vues et de nouveaux types sans changement de type.

## 3. Ce qui manque

a. **Dessins des vues avant, arrière et dessus.** Le dossier ne fournit que le profil droit (`saxo_plan_emplacements.svg`). Il faut les dessiner dans le même `viewBox`, et les faire valider par John. Je ne les invente pas.

b. **Emplacements types par vue.** Aujourd'hui, Capot, Hayon, Lunette arrière et Toit sont `hors_plan` (sans forme). Proposition de répartition, à valider avec John :

| Vue | Emplacements proposés |
|---|---|
| droite | Portière, Custode arrière, Aile avant, Aile arrière, Bas de caisse, Bandeau de pare-brise (déjà en place) |
| avant | Pare-chocs avant |
| arriere | Hayon, Lunette arrière, Pare-chocs arrière |
| dessus | Capot, Toit |

Les emplacements sans forme restent en `hors_plan` jusqu'à leur dessin, comme aujourd'hui.

c. **Véhicules déjà créés.** `emplacementsDepuisGabarit` ne tourne qu'à la création du véhicule. Un véhicule existant ne recevra pas les nouveaux emplacements. Il faut un complément, idempotent (même véhicule, même vue, même nom : aucun doublon), déclenché par un utilisateur.

d. **Version du gabarit.** Le véhicule ne stocke que `gabarit_cle` (`services-serveur.ts`, ligne 192). La version n'est pas enregistrée : « incrémenter la version » n'a aucun effet sur les véhicules existants. Deux options (voir §5).

## 4. Proposition en deux étapes

### Étape 1 : code, sans toucher aux données (après accord)

- Choix d'emplacement pour une convention : `listerEmplacementsPourPartenaires` renvoie la vue, et le libellé affiche le côté (« Portière, côté gauche »). Ça règle la liste, sans renommer.
- Limite : le nom copié dans `partenaires_benefit.slot_nom` reste « Portière ». Le côté n'apparaît donc que dans le choix, pas dans la contrepartie déjà saisie. Il faut l'étape 2 pour que le nom stocké porte le côté.
- Gabarit : ajout des vues avant, arrière et dessus, dès que les dessins sont validés, avec les emplacements du §3b en `hors_plan` d'abord.
- Plan : la vue gauche dessine les lignes `gauche` (et plus les miroirs des lignes droite). Pour que ça marche, la forme stockée d'une ligne gauche doit être la forme retournée. Pour les lignes déjà créées, c'est une écriture de données : étape 2.

### Étape 2 : données, avec accord explicite (pas de migration sans ton accord)

Option A, recommandée : **garder les deux lignes, les renommer.**
1. Renommer la ligne droite en « Portière droite » et la ligne gauche en « Portière gauche » (colonne `nom`). Pas de changement de structure.
2. Répercuter le nouveau nom dans `partenaires_benefit.slot_nom`, par la même logique que l'événement `voiture.emplacement_modifie` déjà prévu (article 951, §6).
3. Corriger la forme des lignes gauche (retournée, pas copiée).
4. Audit en lecture seule, avant toute écriture (script jetable) : combien d'occupations actives (réservé, posé) sont sur une ligne **gauche** ? Pour chacune, John indique le bon côté. On déplace alors l'occupation vers la bonne ligne (changement de `slot_id`, historique conservé), en respectant l'index d'occupation active unique.
5. `symetrique` : une fois les lignes distinctes, ce champ ne sert plus au rendu. Le garder comme information (« existe en paire »), ou le retirer. Je recommande de le garder : pas de migration à faire pour ça.

Option B : **une seule ligne par emplacement symétrique, plus une colonne « côté ».**
- Plus propre à long terme : la contrainte d'unicité porterait sur (véhicule, type, côté).
- Mais c'est une migration de structure, et il faut réécrire les lignes existantes. Je ne la recommande pas tant que les réservations existantes ne sont pas auditées.

### Ce qui ne change pas

- Les réservations existantes gardent leur emplacement (même identifiant) et leur historique. Seul le nom change, et le côté devient lisible.
- Le lien de la contrepartie vers l'emplacement (`slot_id`) reste valide.

## 5. Version du gabarit et ajout de vues

Deux options :
- **A, recommandée : pas de version.** Le complément du §3c ajoute les emplacements manquants, par (véhicule, vue, nom). Aucune migration.
- **B : colonne de version sur le véhicule** (migration additive). Utile seulement si on veut savoir quel gabarit a produit quels emplacements.
